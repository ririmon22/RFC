# 仮想環境構築と受入試験 — 4ノードのMACsec終端ラボ

目的はLinux AとBがそれぞれスイッチと独立した暗号化リンクを確立し、RADIUS認証とアテステーション評価を経て相互通信できることを検証すること。[統合シーケンス](2端末_MACsec終端_統合シーケンス.md) のゲートを一つずつ追加する。

## 1. 比較する構成

| パターン | 実装 | 立証できる範囲 | 判定の限界 |
|---|---|---|---|
| A. Linux名前空間・静的SA | veth 2組、Linux MACsec 4本、復号側bridge、サーバー用名前空間 | 2区間終端、復号・再暗号化、SecYのフィルタとアプリ疎通 | EAP・MKA・アテステーションは未評価 |
| B. 静的CAKのMKAとvTPM | QEMU/KVMの端末VM 2台、swtpm 2個、スイッチVM、共用サーバーVM | MKAによるSAK導入・更新とQuoteの試験。EAP/RADIUSを別段階で検証可 | 静的CAKで出た結果はEAP由来CAKの立証にならない |
| C. LinuxスイッチVMで動的CAK | BにFreeRADIUS、macsec対応のSupplicant/Authenticator、認可制御を追加 | EAP由来CAK、MKA、TPM、2ポートの認可と転送を統合 | 採用ビルドの有線認証、動的CAK、ポート制御連携が必要 |
| D. ベンダー仮想スイッチ | CのスイッチVMを仮想NOSに変更 | 製品の管理面、CoA等。仮想で実装されていればMACsecまで立証 | 実機ASIC依存のSecYを仮想NOSが提供するか実測 |

Aを起点とし、最終目標はC。Dは仮想NOSがMACsec終端と必要なルールを実装する場合の比較対象。単純bridgeでAとBの生インターフェースを接続するとスイッチ終端の試験条件を満たさない。

## 2. インターフェースと管理経路

| 場所 | 割当例 | 目的 |
|---|---|---|
| Linux A/Bのアクセス | 各 `eth0` → スイッチVMの `lan-a` / `lan-b`。ホスト側はポートごとに別の仮想L2 | 親NICでEAPOL/MKAとMACsecを観測。IPは端末のMACsecデバイス上 |
| スイッチのデータ面 | `ms-a` / `ms-b` → bridgeまたは同等の転送面 | 各アクセスリンクを独立に終端。ルールは復号側の両方向で強制 |
| RADIUS管理 | SW `192.0.2.2/24` → Server `192.0.2.10/24` | NAS管理経路。A/Bから直接到達させない |
| 隔離サービス | A `198.51.100.11/24`、B `198.51.100.12/24`、Server `198.51.100.10/24` | 認証・SA成立後のVerifier到達性。Serverは管理と隔離をブリッジしない |
| 管理コンソール | 仮想シリアルまたはハイパーバイザー | 故障注入時もアクセスネットワークを迂回させない |

ACL方式なら端末間のIPv4/IPv6、ARP/ND、ブロードキャスト転送も隔離状態で評価する。初期のラボでは静的IPv4、既知のサーバー宛て、IPv6・その他EtherTypeは明示的に評価または制限する。隔離中のARPを許可する際は同じポートの管理サービスへの到達だけが開き、A/B間のアドレス解決と通常データが遮断される条件を検査する。

## 3. パターンAの構築例

専用ラボホストのroot Bashで実行する。Linux MACsec、veth、bridge、iproute2が必要。名前空間名が空いていることを確認してから開始する。以下は短時間の検証用。4つの方向に独立した使い捨てSAKを使い、同じ鍵でPNを巻き戻す再構築を避ける。

```bash
set -euo pipefail
for ns in rfc-a rfc-b rfc-sw rfc-srv; do
    ip netns add "$ns"
    ip -n "$ns" link set lo up
done
ip link add a0 netns rfc-a type veth peer name sa0 netns rfc-sw
ip link add b0 netns rfc-b type veth peer name sb0 netns rfc-sw
ip link add srv0 netns rfc-srv type veth peer name ss0 netns rfc-sw

mac_of() {
    ip netns exec "$1" cat "/sys/class/net/$2/address"
}

secure_pair() {
    local endpoint="$1" parent="$2" sw_parent="$3" sw_macsec="$4"
    local endpoint_mac switch_mac endpoint_key switch_key
    endpoint_mac=$(mac_of "$endpoint" "$parent")
    switch_mac=$(mac_of rfc-sw "$sw_parent")
    endpoint_key=$(openssl rand -hex 16)
    switch_key=$(openssl rand -hex 16)

    ip -n "$endpoint" link set "$parent" up
    ip -n rfc-sw link set "$sw_parent" up
    ip -n "$endpoint" link add link "$parent" ms0 type macsec port 1 encrypt on protect on validate strict replay on window 0
    ip -n rfc-sw link add link "$sw_parent" "$sw_macsec" type macsec port 1 encrypt on protect on validate strict replay on window 0

    ip -n "$endpoint" macsec add ms0 tx sa 0 pn 1 on key 01 "$endpoint_key"
    ip -n rfc-sw macsec add "$sw_macsec" rx port 1 address "$endpoint_mac"
    ip -n rfc-sw macsec add "$sw_macsec" rx port 1 address "$endpoint_mac" sa 0 pn 1 on key 01 "$endpoint_key"
    ip -n rfc-sw macsec add "$sw_macsec" tx sa 0 pn 1 on key 02 "$switch_key"
    ip -n "$endpoint" macsec add ms0 rx port 1 address "$switch_mac"
    ip -n "$endpoint" macsec add ms0 rx port 1 address "$switch_mac" sa 0 pn 1 on key 02 "$switch_key"

    ip -n "$endpoint" link set ms0 up
    ip -n rfc-sw link set "$sw_macsec" up
}
secure_pair rfc-a a0 sa0 ms-a
secure_pair rfc-b b0 sb0 ms-b

ip -n rfc-sw link add br0 type bridge
for port in ms-a ms-b ss0; do
    ip -n rfc-sw link set "$port" master br0
    ip -n rfc-sw link set "$port" up
done
ip -n rfc-sw link set br0 up
ip -n rfc-srv link set srv0 up
ip -n rfc-srv addr add 198.51.100.10/24 dev srv0
ip -n rfc-a addr add 198.51.100.11/24 dev ms0
ip -n rfc-b addr add 198.51.100.12/24 dev ms0

ip netns exec rfc-a ping -c 3 198.51.100.12
ip netns exec rfc-b ping -c 3 198.51.100.11
ip -n rfc-sw -s macsec show
```

別ターミナルで `ip netns exec rfc-sw tcpdump -eni sa0 'ether proto 0x88e5'`、`sb0`、`ms-a icmp` の3点を観測する。A側とB側は別々のSecY／SAカウンタ、復号側で内側パケットを確認する。短いpingで成立後にMTU付近も測る。親NICからの平文フレームがあっても通常アプリが受信しないことを確認する。後片付けはラボプロセスを停止後、自分が作成した4名前空間だけを `ip netns del <名前>` で削除する。

## 4. パターンB/Cへの移行と機能ゲート

1. A/Bをそれぞれ別のQEMU/KVM VMに置く。OVMFの変数ストア、仮想ディスク、swtpmソケットと状態をVMごとに用意する。[QEMU TPM仕様](https://www.qemu.org/docs/master/specs/tpm.html) に従い、例ではswtpmキャラクタデバイス、`-tpmdev emulator`、対応する `-device tpm-tis` を接続する。ゲストでデバイス・PCR・ブートログを確認。
2. 親NICに設定した静的SAを終了し、動的にセッションを管理する。一つのリンクを事前共有CAK/CKNで検証し、MKAの送受、SAK導入、鍵更新と二つ目のリンクの独立性を確認する。CAKをリンク間で使い回さない。
3. [既存設定ガイド](8021X_RADIUS_三者の設定対応と統合シーケンス.md) と [FreeRADIUS EAP-TLS公式チュートリアル](https://www.freeradius.org/documentation/freeradius-server/3.2.11/tutorials/eap-tls.html) に従い、EAP-TLSとRADIUSを構成する。管理側IP、NAS登録、信頼CA、証明書名、ユーザー／端末ID、RADIUS方式を固定する。事前共有鍵を外して動的CAKを単独で試し、静的経路の混入を防ぐ。
4. wpa_supplicant／hostapdは対象パッケージのMACsecドライバとKaYの有無、動的CAK、ポート別インスタンス、復号後インターフェースを確認する。無線用／wired用の設定を踏襲しても、必要なMACsecドライバとスイッチの制御面が成立するかは別の実測。ルール強制は有線データ面で検証する。
5. [Keylime公式資料](https://keylime.readthedocs.io/en/latest/) に合わせて各端末にAgent、サーバーにRegistrar/Verifierを配置する。A/BのAKを別々に登録し、隔離側からの到達方向と必要ポートを採用版の構成から確定。PASSをポートセッションへ束縛したうえで、NASに認可を適用する。
6. 最初はACLでIPが変わらない構成を使う。CoAで変更する場合は属性対応、応答、再認証と適用実態を確認する。仮想NOSによっては管理APIが必要。

## 5. 最終受入試験

| ID | 条件 | 許可される交通と必要証跡 |
|---|---|---|
| V1 | 両端未認証 | 親NICに制御フレーム。A/B間の通常L2/L3は不通 |
| V2 | EAP合格、片側だけMKA不成立 | 対象ポートの通常通信は不通。Accept、MKA失敗、遮断を個別に確認 |
| V3 | EAPとMKAは両方合格、BのみQuote不合格 | A–B双方が不通。隔離Verifier経路がBにも残る |
| V4 | 両端のEAP・MKA・Attestation合格 | A→BとB→AのTCP、両アクセスリンクのMACsec、復号側転送を同じ時間帯で確認 |
| V5 | 通常通信中にB切断→再接続 | 旧BのPASSで開かない。Aのセッションに影響しない |
| V6 | Verifier停止・認可結果期限切れ | 設計値までにA/Bの通常通信が止まる。制御点から測った停止時間を記録 |
| V7 | スイッチ管理経路の停止 | NAS側のローカル期限或いは安全な既定状態が効く。CoAの送信だけでは合格にしない |
| V8 | 鍵更新・MTU境界 | 再鍵中の損失量、SAの切替、最大内側フレーム、IPv4/IPv6の振る舞いを記録 |
| V9 | 暗号化必須なのに平文を送信 | 解析用テストトラフィックが受信アプリに到達せず、拒否の理由かカウンタを確認 |

記録にはVMスナップショット識別、パッケージ版、3地点のキャプチャ、スイッチとFreeRADIUSのログ、Verifier判定、試験ごとの開始・終了時刻を含める。鍵、共有秘密、不要なデバイス識別情報は除く。パターンA～Dを実行して立証する範囲は別々に採点する。

設計演習では、スイッチ内で読めてよい情報、両端mTLSを追加する際の証明書の目的、Bを隔離したままAが別の許可済みサービスを使えるかを定義する。仮想NOSの機能が足りない場合は、構成Cのどの機能まで代替可能かを証跡で示す。
