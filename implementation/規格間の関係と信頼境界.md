# 規格間の関係と信頼境界 — Linux 2台・MACsec終端スイッチ

## 1. 4ノード上の役割

| ノード | 役割 | 信頼するもの | 終端する通信 |
|---|---|---|---|
| Linux A | Supplicant、MKA Participant、SecY、Attester | EAPサーバーCA、登録済みの管理サービス、ローカルの起動信頼設定 | A↔SWのMACsec、A↔EAP ServerのEAP-TLS、A↔Verifierの管理通信 |
| Linux B | Aと同じ役割。独立したID・鍵・接続状態 | B自身の登録と信頼設定 | B↔SWのMACsecおよびBの管理通信 |
| スイッチ | Authenticator、NAS、ポート別MKA/SecY、強制点 | RADIUSピア、認可制御元、ポート別SA | A側とB側で独立したMACsec。RADIUSは管理経路 |
| 共用サーバー | EAP Server、RADIUS、Verifier、論理的なRelying Party | CA、AK台帳、参考値、NASセッション | RADIUS、Evidence転送、認可コントローラの更新経路 |

スイッチはA側で検証・復号したフレームを内部で転送判断し、B側でそのリンクの鍵を用いて保護し直す。スイッチ内にも見せたくないアプリケーション内容はA–B間でTLS/mTLS等を重ねる。この場合も外側Ethernetでは独立した二つのMACsecが動作する。

## 2. 役割と原典の対応

| 境界 | 主な文書 | 次の境界へ渡すもの |
|---|---|---|
| デバイス認証 | [IEEE 802.1AR・802.1X](../standards/ieee/README.md)、[RFC 9190](../standards/RFC9190_EAP_TLS13_日本語詳細解説.md) | 検証済み証明書IDとEAPセッション |
| AAAバックエンド | [RFC 3579](../standards/RFC3579_RADIUS_EAP_日本語詳細解説.md)、[RFC 5247](../standards/ietf/RFC5247_EAP_Key_Management.md)、[RFC 3580](../standards/RFC3580_IEEE8021X_RADIUS_日本語詳細解説.md) | 認証結果、鍵材料、初期認可 |
| リンク鍵とデータ | [IEEE 802.1X MKA・802.1AE](../standards/ieee/README.md) | リンク別のMKA状態とデータ面のSA状態 |
| 測定・期待値 | [TPM Library](../standards/tcg/TPM2_Library.md)、[Firmware Profile](../standards/tcg/PC_Client_Firmware_Profile.md)、[RIM](../standards/tcg/PC_Client_RIM.md) | Quote・ログ・発行者付き参考値 |
| 評価責務・証跡表現 | [RFC 9334](../standards/ietf/RFC9334_RATS_Architecture.md)、[RFC 9683](../standards/ietf/RFC9683_TPM_Remote_Integrity_Verification.md)、[RFC 9684](../standards/ietf/RFC9684_CHARRA.md)、[RFC 9711](../standards/ietf/RFC9711_EAT.md) | 登録済みAttesterの評価。輸送／表現は採用方式で決定 |
| 変更と復旧 | [NIST SP 800-193](../standards/nist/SP800-193_Firmware_Resiliency.md) | 更新後・復旧後に再評価すべき構成 |
| コンポーネント拡張 | [DSP0274](../standards/dmtf/DSP0274_SPDM.md)、[DSP0277](../standards/dmtf/DSP0277_Secured_Messages.md) | 採用時に周辺機器の認証・測定結果 |
| 権限反映 | [RFC 5176](../standards/RFC5176_CoA_Disconnect_日本語詳細解説.md) またはNASの管理API | 対象セッションと変更の応答、実際のACL・VLAN状態 |

CHARRAはYANG RPC、EATはClaims形式。Keylimeを採用する基本構成ではKeylimeの転送形式を用いるため、この二つは独立した相互運用の拡張演習になる。SPDMは周辺機器とのローカル信頼境界に追加する。複合アテステーションの参考値は対象コンポーネントと出所ごとに照合してからポリシーで集約する。

## 3. IDを生成・取得する場所

| 値 | 生成・取得元 | 用途と注意 |
|---|---|---|
| 外部EAP Identity | Supplicantの設定 | EAP-Response/Identityに入る。EAPOL-Startの本文は空。外部ID単独で登録端末と認定しない |
| 検証済みEAP証明書ID | 証明書発行とEAP Serverの検証 | 台帳の端末IDへ写像。更新時の証明書世代を記録 |
| NAS ID・ポート | スイッチ設定および物理／仮想インターフェース | 強制点の識別。MACアドレスだけに依存しない |
| Acct-Session-Id・ローカル世代 | NASと認可コントローラ | 認可対象。DisconnectやLink Downで無効化 |
| SCI | SecYのシステム識別部とPort Identifier | 保護チャネルの特定。端末のアプリIDに使わない |
| AK識別子・端末ID | 登録の際に公開鍵と台帳から確定 | Verifierが証明書IDと同じ端末を指すかを検証 |
| nonce | Verifier | チャレンジの鮮度と一回性を検証 |

設計演習では、A/Bが同じ外部Identityを送る場合に最終的に何で区別できるか説明する。ポート・証明書更新・TPM交換のどれが発生しても、台帳に残す履歴と失効条件を定義する。
