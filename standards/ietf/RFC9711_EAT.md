# RFC 9711 — Entity Attestation Tokenの構造と検証

[公式原典](https://www.rfc-editor.org/rfc/rfc9711.html)（Standards Track）。原典のClaims、Submods、Profiles、Security/Privacy Considerationsと[媒体型 RFC 9782](https://www.rfc-editor.org/rfc/rfc9782.html)を参照。TPM Evidenceのラップやコンポーネントの状態表現を設計するときの選択肢とする。

## 1. フォーマット

| 要素 | 形式 | 使い方 |
|---|---|---|
| トークン | CWTまたはJWT | 選んだプロファイルで符号化・保護レイヤーを固定 |
| eat_nonce | JSON名。CBORでは対応する登録ラベルを使う | 受信時の再送・リプレイ対策。プロファイルが型・受理条件を具体化 |
| ueid | エンティティの識別に使うClaim | 安定IDの開示が追跡につながるため宛先と保存範囲を制限 |
| eat_profile | 使用プロファイルの識別 | 受信先で許可する値、必須Claim、保護方式を固定 |
| submods | 下位モジュールを表す構造 | 親子関係と出所、入れ子トークンの保護を別々に評価 |

ラボではCBOR/CWTと署名付きCOSEを選び、許容アルゴリズム、Claim型、最大サイズ、最大入れ子深さ、外部トークン参照の可否を仕様書に書く。JSON名をCBOR mapキーへそのまま転記する実装を避ける。表示に使うJSONはデバッグ出力であり、署名対象バイト列は受信したプロファイル準拠の表現で検証する。

## 2. 鍵とシーケンス

1. Verifierが端末ID・要求と対応するnonceを発行する。ラボでは許容するプロファイルを一つに固定する。
2. Attesterは測定状態を収集し、署名者の持つ鍵で保護したClaim集合を生成する。TPM Quoteを添える場合は、その表現とトークンへの暗号的な結合をプロファイルで定める。
3. Verifierは外側の型・長さ・署名方式を制限して解析し、信頼する発行者鍵で検証する。さらにnonce、対象ID、出所、測定値、submodsの関係を検証する。
4. Verifierは評価結果をRelying Partyが消費できるように提供する。用途、発行者、宛先をプロファイルに明記する。

Quoteを作るAK、EAT署名鍵、Verifierの結果署名鍵はスコープが違う。外側トークンに署名する鍵と、内側TPM Quote署名元が同一である根拠は自動では得られない。登録情報や運用プロファイルで対応を決める。

## 3. OSSと設定の対応

CBOR/COSEの部品候補に [t_cose](https://github.com/laurencelundblade/t_cose)、JWTを採用するときは使用するJOSE検証ライブラリの許容署名方式・鍵選択・Claim検証をアプリ側で固定する。汎用ライブラリは署名やエンコードを補助し、RFC 9711のプロファイル適合性や期待値判断はアプリ側の責務になる。Keylime標準の通信をEATとして扱う設計には変換・検証層の仕様が必要。

［設定例］要求ID有効期間30秒、許可Issuerの鍵セットを明示、入れ子深さ2、未知のプロファイルを拒否。これらはRFC既定値ではなく、ラボ内の処理量と証跡を制御する値。

## 4. 検証表と設計演習

| 入力 | 期待する判定 |
|---|---|
| 承認済み署名鍵、正しい型、鮮度・参考値合格 | 受理。対象と評価に使用したプロファイル版を記録 |
| 署名正当・旧nonce | 拒否。使用済み・期限切れを分類 |
| 署名正当だがプロファイルまたはClaim型が違う | 拒否。寛容な型変換や暗黙の既定値で許可しない |
| 子のトークンが別端末に属する | 親子の結合を検証して拒否 |
| 期待した子モジュールのClaimが欠落 | 部分的な成功を最終合格としない |

演習では「本体TPM Quoteと周辺機器SPDM結果を組み合わせる」プロファイルを設計する。測定対象の必須／任意、署名の出所、期待値発行元、欠落時の扱いを決め、外側署名だけが適合したケースの判定理由を示す。
