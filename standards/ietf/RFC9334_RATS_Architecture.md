# RFC 9334 — リモートアテステーションの責務と信頼モデル

[公式原典](https://www.rfc-editor.org/rfc/rfc9334.html)（Informational）。§3のアーキテクチャ、§4の用語、§5のトポロジー、§10の鮮度、Security/Privacy Considerationsを参照。ここではLinux端末の状態とネットワーク認可を例にする。

## 1. 役割と判断を分ける

| 役割 | 本構成の担当 | 入出力 |
|---|---|---|
| Attester | Linux端末A/B | nonceを受け、TPM Quote・測定ログ等のEvidenceを提供 |
| Verifier | 共用サーバーの検証プロセス | Evidence、Endorsements、Reference Values、評価ポリシーからAttestation Resultを生成 |
| Endorser | TPM製造者またはラボ登録基盤 | 鍵や機器の由来を裏付けるEndorsement。vTPMはラボの信頼根拠を明示 |
| Reference Value Provider | 承認済みビルドの管理者 | 機種・版・設定に対応した期待値を提供 |
| Relying Party | 共用サーバーの認可コントローラ | 結果とNASセッション、制御ポリシーを評価。最終的な許可を決定 |
| 強制点 | スイッチの対象ポート | ACL／VLANとSecYの実状態で許可を強制 |

Evidenceが示す内容、Verifierの評価結果、業務アクセスの認可は三段階。例えば保守用イメージは正規署名・許容された測定値を持っていても、通常通信のポリシーでは隔離に留められる。

## 2. フォーマットとモデル

RFC 9334は役割およびメッセージの意味を整理する文書。バイト列はTPM Library、RFC 9684、RFC 9711などの採用したプロファイルで決まる。次の論理フィールドはラボ設計例で、APIのバイト配置やIANA登録名を示すものではない。

| 論理要素 | 例 | 検証時の関連付け |
|---|---|---|
| チャレンジ | ランダムなnonceと要求ID | 1回だけ受理。発行先端末、要求時刻、消費済み状態を記録 |
| Evidence | AK識別子、Quote、署名、イベントログ | AKの登録先、nonce、PCR selection、署名とログを独立に評価 |
| Result | 対象ID、判定理由、ポリシー版、期限、宛先 | 認可側が出所・宛先・鮮度を確認し、現在のNASセッションに束縛 |

**Background Check**ではRelying PartyがEvidenceを受け取りVerifierに評価を依頼する。**Passport**ではAttesterがあらかじめVerifierから結果を得てRelying Partyへ提示する。Verifierが通信を開始するPullと、Attesterが準備を通知するPushは転送の方向に関する選択であり、RATSの2モデルと一対一には対応しない。共用サーバーへVerifierとRelying Partyを置いても、DB権限と結果消費処理を分けられる。

## 3. 正常系と異常系

1. 登録時にEAP証明書ID、Attester ID、AKを結び付ける。登録の権限と端末交換時の承認を記録する。
2. アテステーション経路上でチャレンジを発行し、Verifierが暗号検証と期待値評価を行う。
3. Relying Partyが結果の出所・期限・対象を確認し、NASの接続世代を照合する。
4. ポリシーが許可する場合に制御を更新し、Ackと実フレームで反映を確認する。

| 条件 | 判定と記録 |
|---|---|
| 署名が正しいがnonceが古い | 鮮度失敗。過去のPASSを再利用しない |
| 検証結果が期限内だが切断→再接続済み | スイッチ側世代が違うため権限変更を拒否 |
| 署名は正しいが承認済み期待値が存在しない | unknownとして隔離。ローカルの障害とは別コード |
| Verifier一時停止 | 試験ポリシーでは期限切れまでに通常通信を取り消す。復旧後に新しいチャレンジ |

## 4. 鍵とOSS設定の対応

AKはTPM Quote用。Verifierが結果をサービス間で署名するなら、署名鍵／信頼設定はAKやRADIUS資格情報と分離する。同一ホスト内の直接照会は認可付きローカルAPIやDBとし、APIへの書込み権限をVerifier側に限定する。［設計例］nonce期限30秒、PASS有効期間120秒、再評価周期30秒を出発点とし、待ち行列、タイムアウト、切断時間を測る。時刻の採用元、プロセス再起動後の期限扱い、時計巻き戻しの試験を行う。

[Keylime](https://keylime.readthedocs.io/en/latest/)の Agent、Registrar、Verifierを役割の実装例とする。Relying PartyによるFreeRADIUS/NASへの連携は別途実装し、採用版で取得できる状態と通知方式を確認する。教材の論理フィールドはKeylimeそのもののAPI定義ではない。

## 5. 検証と設計演習

AのEvidence、BのPASS、再接続前のAのPASSを別々に投入し、それぞれ期待どおりに適用・拒否された理由を監査ログで示す。ラボの「期限後10秒以内に通常通信停止」を仮の合格閾値とし、Verifier停止、NAS管理経路停止、リンク再接続を組み合わせて限界を実測する。演習ではPassportを採用した場合に、結果の宛先制限、漏えい時の追跡可能性、証明書更新時のID再登録をどこで行うか設計する。

## 6. 鮮度の選び方

| RFC 9334 §10の方式 | 配備に必要な前提 | 試験 |
|---|---|---|
| 同期時計による明示時刻 | 発行・検証側の時計と許容偏差、時計同期自体の信頼 | 期限内・期限直後・将来時刻・時計巻き戻し |
| nonceによる暗黙の時刻 | 発行元がチャレンジと要求先を安全に保管。署名対象のnonceを評価できる | 同時要求、別端末に発行されたnonce、期限・重複 |
| Epoch ID | 参加者が時代識別子を発行規則と共に認識 | 新旧境界で再送し、許容範囲と再接続を判定 |

本ラボでは、Evidenceにはnonce、認可には現在のセッション世代とローカルの期限を使う。Verifierと強制点が分断されても、期限切れを強制点側が検出できるか確認する。端末から自己申告された「採取時刻」は参考情報としてログに残せるが、これだけでは第三者による鮮度の証拠にならない。
