## 0. この規格で何を理解するか
証明書チェーン、証明書失効、パス検証アルゴリズムの基礎を定義。802.1Xの端末・サーバー証明書、Keylime用TLS証明書、デバイスID証明書は異なる用途で使われ、各用途に適切な信頼アンカーと識別子照合が必要。

## 1. 規格の仕組みを順番に理解する
### 1.1 証明書は何を証明するか
証明書はSubject/SubjectAltName等の識別子と公開鍵を、Issuerの署名で結びつける。署名だけを検証しても、そのIDが求める端末・サーバーかどうかは分からない。アプリケーション固有の名前検証・権限付与が必要。

### 1.2 基本フィールドと拡張
Version、Serial Number、Signature Algorithm、Issuer、Validity、Subject、Subject Public Key Info、Extensionsから構成される。実際のデータ構造はASN.1 DER。`PEM`はDERをBase64エンコードして囲った表現。

### 1.3 Basic ConstraintsとCA資格
BasicConstraintsのcA真偽とpathLenConstraint、KeyUsageのkeyCertSignなどがCAとして証明書を使えるかに関係する。末端の端末証明書を勝手に中間CAとして使ってはいけない。

### 1.4 Key UsageとExtended Key Usage
KeyUsageは署名・鍵暗号化などの用途制約。EKUはTLS serverAuth/clientAuthなどのアプリケーション用途を絞る。802.1Xで端末証明書とRADIUS証明書を区別し、用途とポリシーを検査する。

### 1.5 証明書パス構築・パス検証
末端→中間CA→Trust Anchorへつながるチェーンを構築し、署名・有効期限・BasicConstraints・KeyUsage・名前制約等を検証する。信頼アンカーは単に通信相手が送ってきた任意のCAではなく、事前に管理者が信頼したCA。

### 1.6 失効（CRL）と運用
秘密鍵漏洩やデバイス撤去時に証明書を失効させる。CRLの配布・確認と、OCSP（別RFC群）の利用は設計で決める。隔離中に失効情報へ到達できない場合のfail-openを避け、キャッシュや更新頻度を考慮する。

### 1.7 証明書の更新と信頼アンカーの切替
端末証明書有効期限とCA有効期限を区別する。新旧CAの移行期間、失効した鍵を再利用しないこと、TPMに保持する秘密鍵の交換要否、時刻未同期の初回起動問題を設計する。

### 1.8 IdentityとAttestationの分離
X.509証明書は主に公開鍵と識別子を結びつける。TPM Quoteは現在のPCR値とnonceをAKで署名する別の証拠。EAP-TLS証明書が有効でも、ソフトウェア測定値が信頼できるとは限らない。

## 3. 通信・処理の具体例
```text
Root CA（信頼ストア内）
  └─ Intermediate CA (CA=TRUE, keyCertSign)
       ├─ RADIUS Server Certificate (serverAuth)
       └─ Device 001 Certificate (clientAuth)
```
EAP-TLS端末はサーバー名とrootを検証。RADIUS側は端末証明書を検証し、シリアル・SAN等と端末台帳を照合して認可する。

## 4. OSS設定との対応（原理と実装を区別）

## 深掘りA：X.509証明書は「公開鍵＋属性＋署名」

X.509証明書を端末へ事前配布する理由は、認証中にCAと必ず通信しなくても、サーバーが署名を検証できるから。証明書には端末の公開鍵が入り、秘密鍵は入らない。CAの署名により、証明書内の公開鍵と識別情報が承認されたものであることを検証できる。ただし「署名が正しい」だけでは、当該装置をネットワークへ許可してよいとは限らない。

### 証明書の主要要素

| 項目 | 解釈 | 検証の論点 |
|---|---|---|
| Version / Serial Number | 形式と発行元内の証明書識別 | Issuer+Serialで一意化を考える |
| Issuer / Subject | 発行者と対象 | Subject文字列だけに認可を依存させない |
| Subject Public Key Info | 公開鍵アルゴリズムと公開鍵 | 署名検証、鍵長、許容アルゴリズム |
| Validity | notBefore / notAfter | 時計の正確さ、更新期間 |
| Basic Constraints | CAかエンドエンティティか、pathLen | 偽CAを信頼チェーンへ入れない |
| Key Usage | digitalSignature等 | 鍵が許可された用途か |
| Extended Key Usage | serverAuth/clientAuth等 | EAP-TLS用途との一致 |
| SubjectAltName | DNS名、URI、その他識別 | サーバー名検証・端末ID対応 |
| Authority Key Identifier等 | チェーン構築補助 | 署名チェーンを誤連結しない |

証明書はASN.1 DERで符号化され、PEMはそのDERをBase64でテキスト表現したもの。`openssl x509 -text` で確認できるが、見た目だけで有効と判定しない。

## 深掘りB：証明書パス検証の手順

1. 対象証明書から信頼済みルートまでの候補チェーンを組み立てる。
2. 各証明書の署名、Issuer/Subject整合、Basic Constraints、Key Usage等を評価する。
3. 有効期間、名前制約、証明書ポリシーなどの適用条件を評価する。
4. 利用目的がTLSサーバーかTLSクライアントかに応じてEKU・名前照合を行う。
5. CRL/OCSP等を採用するなら失効状態を評価する。到達不能時の扱いを方針化する。
6. 最後に端末・サーバーの認可DBへ結びつける。CAが署名した任意の端末を自動許可しない。

**信頼アンカーは証明書が自己署名だから自動的に信頼されるわけではない。** 配布済みの信頼ストアやポリシーにより信頼を与える。

### EAP-TLSへの具体適用

SupplicantはRADIUSサーバーの証明書チェーンとサーバー名を確認する。RADIUS側は端末証明書のチェーンとクライアント用途・端末識別を確認する。片方向のCA証明書配布だけでは双方の検証は完成しない。TPM内の非エクスポート鍵を使う場合、TLSライブラリが署名操作へ到達できることも必要。

## 深掘りC：更新と失効は設計時から必要

製造時に証明書を埋め込むだけでは、期限切れ・装置廃棄・鍵漏えい・CA移行を扱えない。期限切れ前の更新、失効証明書の拒否、時刻が未設定の端末の起動直後の扱い、CAローテーション時の二重信頼期間を定義する。CRL/OCSPの利用にはその取得先に認証前でも到達できるかというネットワーク設計問題がある。製造時のIDevIDと運用時のLDevIDを分離する設計が候補になる。

**根拠を読む場所**：RFC 5280 §4（証明書/CRLプロファイル）、§5（CRL）、§6（Certification Path Validation）。端末名前照合の具体則は使うTLSアプリケーションの仕様にも依存する。

## 規格文書を読んで照合する方法
以下の順に原文を確認すると、説明を単純な「機能紹介」で終わらせず、規格に根拠のある設計へ落とせる。
1. 冒頭のScope/Introductionでこの規格が定義しない処理を確定する。
2. Protocol Overview/Message Flowを追い、各メッセージの生成者・検証者・次状態を並べる。
3. Packet Format/Attribute/Extensionの定義から、長さ・値域・順序・必須条件を確認する。
4. Security Considerationsから、なりすまし・改ざん・再送・失効・ダウングレードの例外条件を拾う。
5. IANA Considerations、Errata、Updates/Updated byを確認し、古い番号表や旧TLS挙動をそのまま採用しない。
6. OSSの設定名とRFCの用語が一致しない場合、OSSの実装を確認して対応表を作る。
