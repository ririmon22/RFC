# DMTF DSP0277 — SPDMセッション上の保護メッセージ

[公式原典 v1.3.0](https://www.dmtf.org/sites/default/files/standards/documents/DSP0277_1.3.0.pdf) のFigure 1・Table 1–2、[公開版一覧](https://www.dmtf.org/dsp/DSP0277)。2.0.0も公開されている。DSP0274、DSP0277、輸送バインディングを版の組で固定し、このページは1.3.0の形式を解説する。

## 1. 形式と鍵管理

| 要素 | 1.3.0での観測点 |
|---|---|
| Session ID | 先頭4オクテット。ハンドシェイクで確立したセッションの選択に使用 |
| Sequence Number | ワイヤ上の有無・形式は選択した輸送バインディングに従う |
| Length | 受信領域の境界検査に利用。数える範囲は原典の表で照合 |
| Application Data Length・Random Data | 暗号化＋認証の形式と認証のみの形式で有無が異なる |
| Application Data / MAC | 採用した保護モード・AEAD・バインディングに応じて処理 |

Requester→Responderと逆方向の鍵・IV・シーケンス状態を分離し、同じ鍵でnonceを再利用しない。セッションIDはセッション状態を検索する値で、ID一致だけで真正性が得られるわけではない。鍵更新と終了は [DSP0274](DSP0274_SPDM.md) の対応手順と合わせて管理する。

## 2. 正常シーケンスと設定

1. DSP0274で能力・アルゴリズムを合意し、例としてKEY_EXCHANGE／FINISHでセッションを確立する。
2. 送信側が当該セッション・方向の鍵と状態で保護メッセージを作る。
3. 受信側がセッションを選び、長さと認証タグを検証してからアプリケーションへ渡す。
4. KEY_UPDATEやEND_SESSIONを用いる場合は、旧鍵とセッションの破棄および次フレームの扱いを追跡する。

［ラボ設定］双方で暗号化＋認証を選択し、採用バインディングとリリース、受信最大サイズ、セッションタイムアウトを記録する。数字はラボの設計値として決め、別バインディングからワイヤ配置を移植しない。

## 3. OSS対応と検証

[DMTF libspdm](https://github.com/DMTF/libspdm) の secured message ライブラリと採用バインディング、[spdm-emu](https://github.com/DMTF/spdm-emu) の対応版を照合する。試験は「プロトコル成立」「保護メッセージの検証」「アプリへの受け渡し」にログを分ける。

| ケース | 合格条件 |
|---|---|
| 正規のセッションで双方向送信 | 両端で方向・セッションIDを対応付け、平文は受信側アプリでのみ確認 |
| 不明セッション／終了後フレーム | アプリが受け取らない |
| テストハーネスによる不正タグ／不正長入力 | 検証で拒否し、通常経路へ流さない |
| 鍵更新の片側失敗 | 古い鍵を無期限に使わず、失敗を検出して再確立する |
| バインディング不一致 | 暗黙の変更で通過させず、能力・形式不一致を記録 |

## 4. 設計演習

同一端末でSPDM、MACsec、アプリmTLSを併用する図を書き、三つの鍵の保有者と暗号化の終端を示す。SPDMで保護した周辺機器通信の成功からLinux A/Bの相互接続可否を推定せず、どの観測点を追加すべきか説明する。
