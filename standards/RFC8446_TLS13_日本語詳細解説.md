## 0. この規格で何を理解するか
TLS 1.3はネットワーク越しの通信相手認証、鍵合意、暗号化、完全性保護を提供する。EAP-TLS内部のTLS、Keylime Agent/Verifier通信のTLS、通常アプリ通信のmTLSのいずれでも基本になる。ただしそれぞれの証明書・認可ポリシーは異なる。

## 1. 規格の仕組みを順番に理解する
### 1.1 TLS 1.3ハンドシェイクの目的
ClientHelloとServerHelloで鍵共有と暗号方式を交渉する。ECDHE等の共有秘密からHKDFを用いてハンドシェイク鍵とアプリケーション鍵を導出する。秘密鍵そのものをネットワークに送るのではない。

### 1.2 サーバー証明書による相手認証
CertificateでX.509証明書を提示し、CertificateVerifyでハンドシェイクに関連した署名を示す。CAチェーン、サーバー名、用途、有効期限、失効などの検証が必要。CAに署名されているだけでは接続相手を確定できない。

### 1.3 mTLSはTLS 1.3の相互証明書認証
サーバーがCertificateRequestを送る場合、クライアントは証明書・CertificateVerifyを返せる。mTLSは個々のTLS接続で双方が証明書等で認証される構成を指し、Remote Attestationの成功を意味しない。

### 1.4 鍵スケジュールとHKDF
TLS 1.3の鍵導出はEarly/Handshake/Master Secretの段階を持つ。Finishedはハンドシェイク内容の整合性を確認する。単一の共有秘密を全用途で再利用しないため、用途ごとにラベルで鍵を分離する。

### 1.5 Record LayerとAEAD
Application Dataはレコード層でAEAD暗号化・認証される。TLSはIPアドレスやイーサネットヘッダーを保護せず、通信相手へのアクセス制御も自動化しない。隔離ネットワークはACLなどを別に使う。

### 1.6 PSK・Session Resumption・0-RTT
セッションチケット/PSKで再接続を高速化できる。0-RTTはリプレイ耐性の制約があり、認証・認可状態を変更するコマンドなどで慎重な扱いが必要。今回の認証系では原則0-RTTを使わない設計がわかりやすい。

### 1.7 暗号スイートと署名方式の分離
TLS 1.3のcipher suiteは主にAEADとハッシュを指定し、鍵共有グループや証明書署名アルゴリズムは別の拡張で交渉する。TLS 1.2時代の長いcipher suite名をTLS 1.3へそのまま当てはめない。

### 1.8 Alertと失敗の扱い
証明書不正、ハンドシェイク内容の不整合、許容暗号方式なしではTLS Alert等で失敗する。TLS失敗でもネットワークの別経路を通じて検証サーバーをバイパスできないように制御する。

## 2. フィールド・データ・設定値の読み解き
| 項目 | 値・形式の例 | 意味と実装上の注意 |
|---|---|---|
| ClientHello | Handshake Type 1 | 対応版、乱数、拡張、鍵共有等 |
| ServerHello | Handshake Type 2 | 選択された暗号パラメータ |
| EncryptedExtensions | Handshake Type 8 | 暗号化後のサーバー拡張 |
| Certificate | Handshake Type 11 | 証明書チェーン |
| CertificateRequest | Handshake Type 13 | サーバーからクライアント認証を要求 |
| CertificateVerify | Handshake Type 15 | 秘密鍵保有を証明する署名 |
| Finished | Handshake Type 20 | ハンドシェイク完全性 |
| KeyUpdate | Handshake Type 24 | 鍵更新メッセージ |
| AEAD | 例 AES-128-GCM | 暗号化と完全性を同時に提供 |

ここに記載する識別番号・ビット長はプロトコル形式の説明、パス・タイマー・証明書名は設計例またはOSS固有の設定である。RFCが規定しないローカル設定を規格必須と誤解しないこと。

## 3. 通信・処理の具体例
```text
Client → Server: ClientHello (supported_versions, key_share, signature_algorithms...)
Server → Client: ServerHello, {EncryptedExtensions, CertificateRequest?, Certificate,
                  CertificateVerify, Finished}
Client → Server: {Certificate?, CertificateVerify?, Finished}
双方: Application Data (AEADで保護)
```
波括弧はハンドシェイク鍵等で保護される部分を概念的に示したもの。TLS 1.3はPeerごとの鍵方向や再開経路の違いがある。

## 4. OSS設定との対応（原理と実装を区別）
OpenSSL/step-ca/FreeRADIUS/KeylimeのTLS設定はライブラリと実装に依存する。CAの信頼ストア、期待DNS名、EKU、鍵交換グループ、証明書のライフサイクルを別々に確認。`TLS 1.3を有効化`だけでは誤ったCAや認可ポリシーの問題を防げない。

## 深掘りA：TLS 1.3ハンドシェイクを各メッセージで読む

TLS 1.3の基本目的は、双方が通信先の認証（構成によってサーバーのみ／相互）を行いながら、新たな通信鍵を合意すること。証明書自体でアプリケーションデータを暗号化しているわけではない。鍵交換によって共有秘密を作り、HKDFを通じてハンドシェイク用・アプリケーション用の交通鍵を導出する。

```text
Client                                Server
ClientHello + key_share      ------>
                           <------   ServerHello + key_share
                           <------   EncryptedExtensions
                           <------   [CertificateRequest]
                           <------   Certificate
                           <------   CertificateVerify
                           <------   Finished
[Certificate]              ------>
[CertificateVerify]        ------>
Finished                   ------>
Application Data <=================>  Application Data
```

`CertificateRequest` やクライアントCertificateはmTLS時の要素。TLS 1.3ではServerHello以降の多くのハンドシェイクが保護される。`CertificateVerify` はハンドシェイク文脈に対する署名で秘密鍵所有を証明し、`Finished` は導出した鍵とトランスクリプトの一致を検証する。証明書をネットワークで送ることは秘密鍵を送ることではない。

## 深掘りB：HKDFとForward Secrecy

ECDHEなどの（一時的な）鍵交換を用いることで、後でサーバー証明書秘密鍵が漏れても、過去の通信をただちに復号できない性質（forward secrecy）を目指す。HKDF-Extract/Expandから各種traffic secretを導出し、AEAD方式で暗号化と完全性検証を同時に行う。nonce/record sequenceの扱いはライブラリの責務が大きく、独自実装は避ける。

### TLS 1.3とEAP-TLSの差

EAP-TLSの内側にはTLS 1.3のHandshakeが入るが、EAP-TLSは**通常のアプリケーションデータ転送のためのTLSセッションではない**。EAP-TLS 1.3固有の完了条件、0-RTT非利用、protected successはRFC 9190を見る。RADIUS/TLSに使う場合はNASとRADIUSサーバー間の通常TLS輸送路となる。

## 深掘りC：失敗原因の切分け

- `unknown_ca`：証明書チェーンや信頼アンカー不一致。
- `bad_certificate`：証明書形式、用途、署名、ポリシー違反等の可能性。
- `certificate_expired`：時計設定・更新サイクルを確認。
- `handshake_failure`：方式・パラメータ・ポリシーの不一致等。
- タイムアウト：TLS自身ではなくEAPOL/RADIUS/ネットワーク側で断片や再送が詰まっていることもある。

TLSのalertが常に具体的な根本原因を一意に示すとは限らない。鍵や証明書をログに出さず、メッセージ種別・証明書識別子・エラー種別を採取する。

**根拠を読む場所**：RFC 8446 §2（Handshake）、§4（Handshake Protocol）、§5（Record Protocol）、§7（Key Schedule）、§9（Compliance）。
