## 0. この規格で何を理解するか
RADIUSメッセージをTLSで保護するためのトランスポート仕様。端末↔AuthenticatorのEAPOLをTLS化するものではない。NAS↔RADIUSサーバー（またはRADIUSプロキシ間）の区間を保護する。

## 1. 規格の仕組みを順番に理解する
### 1.1 どの区間を暗号化するか
EAP-TLSはPeerとEAPサーバー間の認証方式、RADIUS/TLSはRADIUSクライアントとサーバー間のトランスポート。両者を混同しない。EAP-TLSの中にTLSがあり、そのEAPがRADIUS/TLSで運ばれる構成もあり得る。

### 1.2 TLSトランスポート上のRADIUS
従来RADIUSはUDPで通信するのが一般的。RFC 6614ではTLSのストリーム上でRADIUSメッセージを運ぶ。TCPの接続・切断、TLSの証明書管理、長期接続時の再接続などを別途扱う。

### 1.3 接続先の識別と証明書
TLSを使うだけで正しいRADIUSサーバーと接続した保証にはならない。CAと接続先名・証明書用途を検証する。クライアント側証明書を要求する場合はmTLSの管理が必要。

### 1.4 共有秘密との関係
従来のRADIUS/UDPとRADIUS/TLSでは、RADIUSパケット内の認証フィールドや属性秘匿化について古典的互換性要件が残る。TLSに載せたらRADIUSヘッダーが消えるわけではない。MD5依存の見直しはRFC 9765と区別。

### 1.5 ポートと接続管理
RADIUS/TLSでは通常TCP/2083を利用する。サーバーとクライアントの両方が同じトランスポート仕様・証明書ポリシーに対応する必要がある。UDP/1812にTLSを付けるだけではない。

### 1.6 プロキシ経路の保護
RADIUSの中継を使う場合は各RADIUS区間ごとのTLS接続を管理。プロキシは各区間のTLSを終端し得るため、エンドツーエンドでNASと最終サーバーがTLS通信するとは限らない。

### 1.7 旧方式との共存
移行期間はUDPとTLSの併用になり得る。失敗時に暗号化されていないUDPへ自動フォールバックする設定は、攻撃者によるダウングレードを招く可能性がある。

## 2. フィールド・データ・設定値の読み解き
| 項目 | 値・形式の例 | 意味と実装上の注意 |
|---|---|---|
| トランスポート | TCP + TLS | RADIUSメッセージの通信経路を保護 |
| 既定ポート | TCP/2083 | RADIUS/TLSで用いられるポート |
| RADIUSヘッダー | Code/Identifier/Length/Authenticator | TLS内でもRADIUS構造は存在する |
| 証明書 | X.509等 | TLS双方の認証方針に依存 |
| EAP-Message | Type 79 | RADIUS内のEAPをそのまま利用可能 |

### 表の読み方
ここに記載する識別番号・ビット長はプロトコル形式の説明、パス・タイマー・証明書名は設計例またはOSS固有の設定である。RFCが規定しないローカル設定を規格必須と誤解しないこと。

## 3. 通信・処理の具体例
```text
Supplicant --EAPOL/EAP-TLS--> Authenticator
                                 |
                                 | TCP/2083 + TLS
                                 |   └─ RADIUS Access-Request/EAP-Message
                                 v
                            RADIUS Server
```
EAP-TLSが端末認証を行い、RADIUS/TLSがNAS–Server区間を保護する。

## 4. OSS設定との対応（原理と実装を区別）
FreeRADIUSでTLS listener、CA、サーバー証明書などを設定できる構成がある。ただしhostapdのRADIUSクライアントが利用するトランスポートを直接RADIUS/TLSへ変更できるかは版/ビルドの確認が必要。中継proxy導入によるRadSec終端など代替構成も検討する。

## 深掘りA：RadSecはEAP-TLSとは別のTLS

EAP-TLSはSupplicantとEAPサーバーが行う証明書認証であり、RADIUS/TLS（俗にRadSec）はNAS/ProxyとRADIUSサーバーの**輸送路**をTLSで保護する。両方TLSという名前でも、終端装置も証明書も用途も異なる。

```text
Supplicant --EAPOL[EAP-TLS]--> NAS
NAS --RADIUS over TLS (RadSec)--> RADIUS Server
         ↑ ここは NAS ↔ RADIUS のトランスポート保護
  EAP-TLSの認証終端は Supplicant ↔ EAP Server
```

### TCP/TLSのために変わる運用

従来RADIUSはUDPの1要求ごとに再送・応答対応付けを管理する。RADIUS/TLSはTCP上のTLS接続に複数のRADIUSパケットを運べるため、接続寿命、TLS再接続、パケット長を使ったフレーミング、複数リクエストの対応、障害時のフェイルオーバーを設計しなければならない。代表的なポートはTCP/2083だが、実装側の設定とファイアウォールを合わせる。

## 深掘りB：TLSで保護してもRADIUS認可は別

mTLSを採用すればNASとRADIUSサーバーが相互に証明書を検証できる。ただし「TLSハンドシェイク成功」だけで、その接続相手が任意のNASポートにアクセス認可を与えられるとは限らない。NASの登録・接続元・名前/証明書の対応や、RADIUS属性の信頼ポリシーは別に定義する。

### 認証失敗・切断への対処

- TLS証明書の期限切れやSAN不一致：接続を許可せず、認証不能として隔離。
- TLS接続切断：すでに許可したセッションをいつまで維持するか、再認証・失効を定義。
- プロキシ経由：TLSの保護は隣接するホップ間。エンドツーエンドの認可属性すべてが一体で保証されるとは限らない。
- TLSバージョン・暗号スイート：実装のサポート状況と現行ポリシーに従う。

RFC 6614はExperimentalであり、これを採用するだけで規格・セキュリティ要件がすべて満たされるとは断言できない。RFC 9765のRADIUS/1.1と併せ、採用版・相互運用性を確認する。

**根拠を読む場所**：RFC 6614 §2（Transport Protocol）、§3（RADIUS/TLS規則）、§4（Security Considerations）。
