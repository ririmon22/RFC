# NIST SP 800-193 — ファームウェアの保護・検知・復旧

[公式原典（2018年最終版）](https://csrc.nist.gov/pubs/sp/800/193/final)。§3の設計原則と§4のProtect、Detect、Recoverを参照。対象はプラットフォームのファームウェアと重要データ。ネットワーク認可は本ラボで組み合わせる制御である。

## 1. 何を試験するか

| 責務 | 設計例 | 観測 |
|---|---|---|
| Protect | 更新を署名で認証し、書込みや構成変更を権限制御 | 署名不一致、未承認更新、旧版の扱い |
| Detect | 起動時に相違を検出し、TPMで比較可能な測定結果を証跡化 | ローカル起動ログとVerifierの判定の違い |
| Recover | 信頼できる復旧用コードとイメージから回復 | 復旧の起点、復元対象、再測定と再認可 |

Root of Trust for Update、Detection、Recoveryの責務と、それぞれから次段へ信頼を渡す境界を図示する。復旧イメージの保管場所と検証器が同じ障害で失われる設計では、復旧の前提が成立しない。保護された復旧媒体、真正性確認と回復手順を別々に確認する。

## 2. フォーマット・鍵・設定

NIST SP 800-193は指針で、ネットワークパケットや統一ファームウェア更新バイト列を規定しない。ラボで更新の証跡を比較するなら、対象機種ID、バージョン、ダイジェスト、署名者ID、署名を持つ採用済み更新方式のメタデータを記録する。回復の結果は起動ログ、TCGイベントログ、Quote、Verifier評価を関連付ける。

更新署名鍵、復旧の承認権限、TPM AK、ネットワーク端末鍵を別々に台帳化する。ファームウェアの公開検証鍵の更新、最低許容版、回復イメージのローテーションを同時に計画する。［ラボ設定例］変数ストアと起動ディスクは個別保存し、復旧用イメージは読み取り専用。復旧完了で自動昇格せず、改めて許容版と新しい証跡を評価する。

## 3. 処理順とOSS

1. 承認済み更新を受け取り、対象プラットフォームと真正性を照合する。
2. 更新後の正常起動と測定を確認する。異常時は回復イメージの真正性を検証して回復する。
3. 復旧後の端末を再度測定し、別のポリシー版／起動世代としてRelying Partyへ渡す。
4. スイッチ側は新しいセッションとして通常通信への復帰を判断する。

QEMU／OVMFとswtpmは起動経路の模擬、[fwupd](https://github.com/fwupd/fwupd) は対応機器で更新を扱う例、Keylimeはリモート評価の候補。VMスナップショットは演習のやり直しには使える。実機での独立した復旧用Root of Trustやファームウェア書込み保護をVMで立証したと扱わない。

## 4. 正常系・異常系と演習

| シナリオ | PASSに必要な証跡 |
|---|---|
| 正規更新 | 旧・新バージョン、更新認証、新版の起動状態と測定結果 |
| 更新の真正性不一致 | 更新が適用されず旧版を維持、通常権限の扱いを確認 |
| 更新中断 | ループや破損状態からの復旧可否、手順と復旧所要時間 |
| 署名は正しいが禁止旧版 | 最低許容版や運用ポリシーで拒否 |
| 承認済み復旧版で起動 | 復旧から新しい認可までの経路を再計測。旧PASSが使われない |
| 復旧媒体も無効 | 通常通信せず、手動復旧に必要な状態の記録 |

設計演習として「更新署名鍵の失効と更新途中の中断」を同時に想定する。更新／検知／復旧の主体と、回復イメージの真正性をどの鍵で確認するかを図示する。再起動、測定、RADIUS認証、通信復帰までの時間を測る設計を提出する。
