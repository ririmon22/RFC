## 0. この規格で何を理解するか
EAPのMethodとしてTLSハンドシェイクを運ぶ方式。Wi-Fiや有線802.1Xで端末と認証サーバーが証明書を用いて認証する。TLS 1.3固有の処理はRFC 9190を参照し、旧TLS前提の図をそのままTLS 1.3に当てはめない。

## 1. 規格の仕組みを順番に理解する
### 1.1 誰と誰がTLSを実行するのか
TLSの論理的な通信相手はEAP Peer（Supplicant）とEAP Server（多くはRADIUSのEAPモジュール）。Authenticatorは中継者。端末はサーバー証明書を検証し、サーバーはクライアント証明書と署名・ポリシーを検証する。

### 1.2 EAP外側の構造とTLS内部の構造
Ethernet→EAPOL→EAP→EAP-TLS→TLSというカプセル化。AuthenticatorとRADIUS間ではEAP-TLSのEAPパケットがEAP-Message属性に入る。Wiresharkで各層を順番に展開するとどこでエラーが起きたかを切り分けられる。

### 1.3 EAP-TLSのフラグと長さ
EAP-TLSはTLSメッセージを断片化して運ぶため、FlagsのL（Length included）、M（More fragments）、S（Start）等を持つ。Lがある場合にTLS Message Lengthを伴う。単純なTLS/TCPのパケットをEthernetへ直接流すわけではない。

### 1.4 証明書と鍵の役割
Certificateには公開鍵を結びつけた署名済みデータが載る。秘密鍵は送信しない。TLS内の署名処理によって秘密鍵の所有を示す。端末証明書だけで機器が起動時に健全だったことは証明できない。

### 1.5 検証すべきサーバーID
信頼するCAにより署名された証明書であっても、意図するRADIUS/EAPサーバーIDと一致する必要がある。端末が誤った認証サーバーを信頼すると資格情報を危険にさらす。サーバー名の照合方針を端末側へ事前設定する。

### 1.6 ハンドシェイク後の鍵素材
EAP-TLSの成果としてEAP鍵素材が導出される。802.1Xの下位レイヤーごとの鍵利用や適用は別仕様に依存する。有線802.1XでEAP-TLSに成功しただけでEthernetのデータフレームが暗号化されるわけではない。

### 1.7 断片化と再送
証明書チェーンは大きくなり、EAP-TLSの複数往復が発生する。EAPの再送とEAP-TLS断片化とRADIUS属性分割を区別する。大きな証明書・PQC証明書はMTUや再送の性能評価が重要。

## 2. フィールド・データ・設定値の読み解き
| 項目 | 値・形式の例 | 意味と実装上の注意 |
|---|---|---|
| EAP Type | 13 | EAP-TLS |
| EAP-TLS Flags | 1 byte | L/M/Sなどのフラグ。予約ビットの扱いは原典確認 |
| TLS Message Length | 4 bytes (Lがある場合) | TLSメッセージの総長 |
| TLS Data | 可変長 | TLSハンドシェイク等のデータ |
| EAP Code | 1/2/3/4 | Request/Response/Success/Failure |
| TLS証明書 | X.509 | 秘密鍵は含まれない |
| EAP-Message | RADIUS Type 79 | Backend ServerへEAP-TLSを運搬 |

### 表の読み方
ここに記載する識別番号・ビット長はプロトコル形式の説明、パス・タイマー・証明書名は設計例またはOSS固有の設定である。RFCが規定しないローカル設定を規格必須と誤解しないこと。

## 3. 通信・処理の具体例
```text
端末                      Authenticator                 EAP Server
  |-- EAPOL EAP-Response ------>|-- RADIUS EAP-Message ------>|
  |<--------- EAP-TLS Request --|<------ Access-Challenge ------|
  |====== TLSハンドシェイク（中継を介して複数往復） ======|
  |<------------- EAP Success --|<---------- Access-Accept -----|
```
初期セットアップでCA証明書、端末証明書、端末秘密鍵を準備する。TLS 1.3の場合、メッセージ並びや暗号化境界はRFC 9190・8446で確認する。

## 4. OSS設定との対応（原理と実装を区別）
wpa_supplicant例: `eap=TLS`, `ca_cert=...`, `client_cert=...`, `private_key=...`, `domain_suffix_match=...`。FreeRADIUS例: EAP `tls`モジュール、サーバー証明書・鍵・信頼CA、クライアント証明書ポリシー。設定キーはRFCのパケットフィールド名そのものではない。

## 5. 正常系・異常系で確認すること
- [ ] 不正CAを拒否
- [ ] サーバー名不一致を拒否

## 深掘りA：EAP-TLSは二つのプロトコルが重なっている

EAP-TLSはEAP Type 13の中にTLSのデータを運ぶMethod。TLSがサーバー証明書や秘密鍵所有証明を処理し、EAPが認証方式を制御する。EAP-TLSの `Flags` と `TLS Message Length` はTLS Recordヘッダーと別物。さらに802.1XのEAPOL Length、RADIUSのAttribute Lengthも存在するため、どの層の長さエラーかを分ける。

### EAP-TLSフラグ

EAP-TLSのFlagsには、`L`（総TLSメッセージ長のフィールドが存在）、`M`（More fragments）、`S`（Start）などがある。EAP-TLS開始ではSビット、長いTLSメッセージではL/Mを利用して分割送受信する。特に証明書チェーンが長いとEAP-TLS層の分割が発生する。

```text
EAP Header
  Code=1(Request) / 2(Response)
  Identifier
  Length
  Type=13 (EAP-TLS)
EAP-TLS Data
  Flags = L/M/S ...
  [TLS Message Length (4bytes, L=1の場合)]
  TLS data fragment
```

RADIUSのEAP-Message属性も253byte単位に分けられるが、EAP-TLSの分割境界は独立している。RADIUS側で属性を再構成し、その後EAP-TLS側でTLSデータを組み立てる。

## 深掘りB：相互認証と秘密鍵の扱い

初期セットアップで端末には端末証明書と秘密鍵、サーバーを検証するCAの信頼アンカーを設定する。RADIUS/EAPサーバー側にもサーバー証明書と秘密鍵、端末を検証する信頼アンカーを用意する。認証中に証明書は送信するが、秘密鍵はネットワークに送信しない。署名操作によって保持を証明する。

`identity` を見ただけで端末を許可してはならず、証明書の署名・有効期限・EKU/KU・名前・失効状態・証明書チェーンを、利用目的に応じて検証する。端末証明書の鍵をTPMに置く場合でも、AK/EKでTPM Quoteを行うRemote Attestationとは別の信頼機能になる。

## 深掘りC：TLS 1.3との版の関係

RFC 5216は歴史的なEAP-TLS仕様であり、TLS 1.3利用時の更新はRFC 9190が規定する。したがって現在のTLS 1.3設計にRFC 5216のシーケンスをそのまま適用するのは危険。例えばTLS 1.3の鍵交換・メッセージ・保護された成功通知はRFC 9190側を優先して読む。

**根拠を読む場所**：RFC 5216 §2（Protocol Overview）、§3（EAP-TLS Packet Format）、§5（Security Considerations）、RFC 9190。

## 規格文書を読んで照合する方法
以下の順に原文を確認すると、説明を単純な「機能紹介」で終わらせず、規格に根拠のある設計へ落とせる。
1. 冒頭のScope/Introductionでこの規格が定義しない処理を確定する。
2. Protocol Overview/Message Flowを追い、各メッセージの生成者・検証者・次状態を並べる。
3. Packet Format/Attribute/Extensionの定義から、長さ・値域・順序・必須条件を確認する。
4. Security Considerationsから、なりすまし・改ざん・再送・失効・ダウングレードの例外条件を拾う。
5. IANA Considerations、Errata、Updates/Updated byを確認し、古い番号表や旧TLS挙動をそのまま採用しない。
6. OSSの設定名とRFCの用語が一致しない場合、OSSの実装を確認して対応表を作る。
